01 New in 5.4.0

233 commits later, it is no longer just memory.

The 5.4 release turns the work pipeline into a full delivery system: run a task as a team, hand over a goal and walk away, and prove the result against the live product.

new

/mb team

Parallel tracks in one working tree.

Split a task into tracks with owned file globs. Each track is a role agent running the full /mb work loop; waves, locks, shared foundations and a scoped commit keep them out of each other's way.

How a team runs → rebuilt

/mb drive

Plan every acceptance criterion with you once, then execute without you — through /mb work and /mb team — until a deterministic firewall is green, the budget ends, or a human decision is needed.

02 The problem

Agents write code fast. Left alone, they drift.

i.

Amnesia

Every session starts cold. Yesterday's decisions are gone, the plan is re-explained, and compaction erases whatever the agent finally learned.

ii.

"Done" without proof

The agent says the feature works. Nobody ran the suite, read the diff against the plan, or clicked through the product. Vibes are not evidence.

iii.

One agent, one lane

Run two sessions in the same repo and they overwrite each other. Run one and a three-module feature takes all afternoon.

03 The framework

Six layers. Use one, or all of them.

Each layer is plain markdown, YAML and shell next to your code, and each one works without the layers above it. Start with memory; add process when the task earns it.

  1. L1 Memory remembers Status, plans, decisions and past sessions in .memory-bank/, read at every session start. /mb start · /mb done · /mb recall
  2. L2 Rules constrain Key rules, TDD, architecture boundaries and 20+ presets — always loaded, under 3 KB. /mb rules · /mb profile
  3. L3 Specs shape A raw request becomes a brief, EARS requirements, a spec triple and a plan with a Definition of Done. /mb brief · discuss · sdd · plan
  4. L4 Pipeline executes Role agents implement each item under TDD; verifier, reviewers and a judge join by preset. /mb work
  5. L5 Team parallelises Several tracks at once in one tree, each with its own files, pipeline and report. /mb team
  6. L6 Drive finishes A goal file with acceptance criteria, driven to completion without you in the loop. /mb goal · /mb drive

Across every layer

Code graph sees

Who calls this, what breaks if it changes, which tests cover it — answered from a committed graph instead of a grep guess.

mb-graph.sh who-calls · impact · tests

Across every layer

Gates prove

Tests, lint, diff scope, protected paths, acceptance criteria and QA bugs — one firewall with one exit code decides whether work is done.

/mb verify · /mb qa · firewall

04 The flow

From a raw idea to verified code.

One path, eight stations, each leaving a file behind. How many stations a task visits depends on its size — a typo does not get a ceremony, a payment flow does not get a shortcut. Pick a size to see its route.

05 The pipeline — /mb work

Process is a dial, not a tax.

/mb work takes a plan or a spec and runs each item through a chain of subagents. Four presets set how long that chain is. Canonical order is fixed; an invalid chain fails before any code is touched.

Routes, firewall and cost →

Models by role, not by habit

A cost tier maps every role class to a model slot. The default, optimal, puts thinking roles on the premium model and doing roles on the mid one. 

cost: optimal   # premium | optimal | economy
# planner · reviewer · judge → premium
# implementer · verifier     → mid
model_profiles:
  claude-code: {premium: opus, mid: sonnet}
  codex: {premium: gpt-6-astra, mid: gpt-6.1-sol}

/mb cost reports what a run actually spent — per session, per role, per work item.

Routes with a floor

/mb analyze-task classifies the work into one route; /mb flow <route> pins it by hand.

  • research a spike; the report is the result
  • bugfix reproduce → debug → patch
  • code-change the default, inside existing seams
  • arch contracts, domain rules, ports
  • migration schema or data, with ordering risk

Touch domain/, a port or a protected path and the route is raised to arch. An override can raise a route, never lower it.

One firewall, one exit code

mb-flow-verify.sh fans out to every check and owns the verdict. A flow is never declared finished on red.

  • acceptance
  • tests
  • diff scope
  • protected paths
  • QA bugs
  • rules
  • lint
  • no TODOs

0 pass · 1 a check is red, named with its findings · 2 a check itself broke — never swallowed as a pass.

06 Parallel tracks — /mb team

Several agents, one working tree, zero collisions.

A team runs one task as tracks. Each track is a role agent that owns a set of file globs, runs the complete /mb work loop for its part, writes one report and talks only to a shared board. You see the plan and say yes before the first dispatch.

Read the /mb team guide →

Files have one owner

Every track declares its globs and dependencies; waves are computed from both. Two tracks whose globs overlap never run at once, and heavy shared commands — a native build, the full suite — wait in a fair FIFO lock queue.

No copy-paste foundations

When several tracks need the same mechanism, the plan stops and proposes a foundation track. A registry of shared mechanisms tells every prompt "use this, do not copy it" — a second copy is a review blocker.

Contracts that execute

A track can carry a frozen contract: spec, rules and DoD checks that must be red before the work and green after it. The commit runs it again and refuses a changed lock. Nothing is pushed for you. 

# a team is three commands and a loop
/mb team init checkout --goal G-004 --max-parallel 4
/mb team track add A --role backend --files 'api/**' --size standard \
     --task "Card payments endpoint" --dod "An unknown card is refused with 402 and a test proves it"
/mb team plan      # tracks, waves, pipeline per track — you confirm
/mb team next      # one action per line: dispatch · fix · collect · stop_human · stop_success

Stateless by design: everything resumes from team.json, the brief, the reports and the board after a compaction or a restart.

07 The goal loop — /mb drive

Vibes in. Evidence out.

Write the end state as acceptance criteria. Drive plans every criterion with you, takes one batch of approvals, then runs on its own. The agent's feeling that the work looks finished is never a stop — only evidence is.

Read the /mb drive guide → 
# .memory-bank/goal.md
## Acceptance criteria

- [ ] Users can pay by card
  - plan: plans/2026-11-20_feature_checkout.md
  - check: bats tests/bats/test_checkout.bats
- [ ] Guests can check out without an account
  - plan: plans/2026-11-20_feature_guest.md

A tick only counts when it is backed

A criterion is met when every linked plan is closed and its check: command exits 0. A checkbox ticked by hand, without that evidence, is listed as unbacked and ignored.

Several drives can share one bank, each with its own goal and budget. On Pi, a settle gate resumes an unfinished run the session owns.

08 Code graph

The agent stops grepping and starts knowing.

/mb graph parses your code into a deterministic graph of modules, functions, classes, imports, calls and inheritance, stored as a committable file next to your plans. Agents query it before they edit; the pipeline feeds it into their prompts.

Three questions, one command

mb-graph.sh who-calls WriteFile   # direct callers
mb-graph.sh impact    WriteFile   # everything that breaks
mb-graph.sh tests     WriteFile   # tests that cover it
mb-graph.sh search "token refresh" # by meaning

Deterministic answers in under a second, with no false hits from strings and comments. search sends an identifier to BM25 and a phrase to local embeddings.

Wired into the pipeline

  • /mb work injects a bounded ## Graph block into implementer, reviewer and judge prompts.
  • A hook notices structural greps and answers with a runnable graph command naming the real symbol.
  • The graph refreshes after every finished item and reports its own staleness honestly.
  • tests follows the chain bats → shell → Python, so a shell change finds its Python tests.

Languages

Python, Bash and Bats always on with zero dependencies. Go, JavaScript, TypeScript, Rust and Java through tree-sitter.

Analytics

God nodes, Louvain communities with cohesion scores, bridge files by betweenness — the same clusters in every process.

Hidden coupling

--cochange mines git history for files that change together without importing each other — coupling no parser can see.

Wiki & warm index

/mb wiki writes an article per module cluster; --apply warms the semantic index so the first concept search is instant.

Unlike a per-request repo map or a server-side index, the graph is a persistent file in your repo: incremental by SHA-256, readable with jq, reviewed in pull requests. How it works and an honest comparison →

09 Acceptance QA — /mb qa

Tests prove the code. QA proves the user path.

A scenario is a short markdown file. The mb-qa-runner agent walks it against the running product like a user would — in a browser through Playwright, on the CLI, or over HTTP — and records exactly what it observed.

Read the /mb qa guide →

Declared at plan time

/mb plan writes qa: on for standard and larger work and has the QA agent draft the cases before any code exists.

Run what you need

/mb qa run all, one scenario by name, a tag like @smoke, or a whole folder.

Regressions stay caught

A fixed bug leaves a regression case behind under qa/test_cases/, so the next run checks it again.

10 Memory — where it all started

The next session already knows.

Everything above writes into one directory. The agent reads it at session start, updates it as it works and hands it to the next session — or the next agent — intact.

Recall, model-free

Lifecycle hooks capture every session. /mb recall "why postgres" searches agreements, progress, notes and past chats with BM25 — no model call.

Agreements that stick

/mb agree pins a decision as AGR-NNN. A changed decision supersedes the old one, and a 4 KB index of the active ones opens every session.

Compaction is survivable

An orchestrator running background agents keeps a short console of open questions and running tracks, and reads it first after a compaction.

Private by construction

Markdown and JSON on your disk, nothing sent anywhere. Keys and tokens are redacted before session capture reaches the disk.

12 Hosts

One bank, nine coding agents.

Project state lives in your repo, not in a vendor's cloud. Adapters teach each host the same model and merge into your existing config idempotently — switch tools mid-project and nothing is lost.

Claude Code

Native commands, lifecycle hooks, named subagents, session memory, a context statusline.

Codex

Global lifecycle hooks and every role as a TOML subagent, read-only where it should be.

OpenCode 2.x

Native command and tool hooks, run-scoped model routing, rendered agents.

Cursor

Global rules, hooks, commands and installed agents that carry their tier model.

Pi Code

A native extension: dispatcher, session capture, and a gate that resumes unfinished runs.

Hermes new

A plugin that runs the skill unchanged, with a bank per folder, project or profile.

Windsurf

Cascade hooks and project rules.

Cline

.clinerules integration and hooks.

Kilo

Rules, with a git-hook fallback where native hooks are absent.

13 Install

Fast to add. Easy to keep. Trivial to remove.

Plain files, marker-based merges, idempotent installs. No hosted dependency and no hidden state. macOS, Linux and Windows (Git Bash or WSL).

pipx install memory-bank-skill
memory-bank install

memory-bank install \

/mb init          # once per project
/mb start         # every session

/mb verify

/mb discuss checkout

/mb drive                # and let it run

14 Documentation

Honest answers, and the long version.

Do I have to use the whole framework?

No. Memory works alone, rules work without a bank, and the pipeline only starts when you ask for it. Task tiers exist precisely so a small change is done inline and only risky work pays for review and a judge.

What does a governed run cost?

About 8 subagent dispatches per item when clean, up to ~25 with fix cycles, plus one verifier per plan. The default medium preset is one dispatch per item. /mb cost reads your transcripts and reports the real numbers.

How do parallel agents avoid overwriting each other?

Each /mb team track owns file globs, overlapping tracks never share a wave, heavy commands queue behind a lock, and sessions coordinate through an append-only board with FREEZE entries. Commits are scoped to the track's files.

Does this replace my agent's built-in memory?

It complements it. Native memory is per user and cross-project; .memory-bank/ is per project and shared with the team. Both load.

Is my code sent anywhere?

No. The graph, BM25 search, co-change analysis and recall index run on your machine for $0. The only model calls are the ones your agent already makes.

Will it overwrite my AGENTS.md or hooks?

No. Adapters write marker blocks and merge idempotently. Your content is kept; uninstall removes only what the skill owns.

Is it production-ready?

v5.4.0 is the current stable line, used daily on real projects, behind 7,000+ tests (pytest, bats, node) on Python 3.11 and 3.12 across Ubuntu and macOS. The skill develops itself with its own memory bank, teams and drive.
