## Diagnosis (plan step 1, read-only; the user's cache was never modified)

- Interpreter: `~/.claude/hooks/.venv/bin/python` (Python 3.14, fastembed 0.8.0). The repo `.venv` has no fastembed, so `mb-semantic-search.py` re-execs into the hooks venv (AGR-047). `FASTEMBED_CACHE_PATH` and `HF_HOME` are unset.
- `EmbeddingRetriever._ensure_model` called `TextEmbedding(model)` without `cache_dir`. As a result, FastEmbed used `tempfile.gettempdir()/fastembed_cache` = `/var/folders/p8/…/T/fastembed_cache/models--qdrant--all-MiniLM-L6-v2-onnx`.
  - Snapshot: `d13954661f83…`.
  - `model.onnx` resolves through `blobs/bbd7b466…` to the shared `blobs/48/489ad214…` (90 387 630 bytes).
- Metadata mismatch: in `files_metadata.json`, `model.onnx` has `blob_id 672677e7…`, but the local blob is named `bbd7b466…` (git oid versus LFS sha256). FastEmbed checks only file sizes offline, so this mismatch does not cause the failure. Experiments ran on copies in `/tmp/mbdiag.*`.
- The project's corpus matrix `.memory-bank/.index/codesearch/embeddings.npy` was warm (`.index.status` = built).
- Reproduction: a fresh process with a different or purged `TMPDIR` and `HF_HUB_OFFLINE=1` ran `mb-graph.sh search "restore recent session summaries into context" --json`.
  - Result: a `ValueError: Could not load model sentence-transformers/all-MiniLM-L6-v2 from any source.` traceback, exit 1, empty stdout.
  - With the original `TMPDIR`, the same query worked (backend embeddings).
- Root cause: model files sit in the OS temp directory, which macOS purges and which a sandboxed or restarted process can see under a different path. A warm matrix then made the search crash instead of falling back. Session recall (`hooks/lib/semantic_embed.py`) already used `~/.cache/fastembed`.

## Deviations

- Tools no longer accept `projectRoot`/`mbPath` parameters, because a model-supplied path could read another project and trigger catch-up writes there.
- Non-zero exit or `ok:false` now throws (a Pi error result) instead of returning the JSON.
- Bats `test_graph_rag_adapters` tests 1, 5 and 6 pinned the old source text and were rewritten to pin the new contract (5 and 6 merged into one).
- The bank is resolved from `ctx.cwd` exactly as in Stages 1/2 (`_lib.sh`, no walk-up). A Pi session started in a project subdirectory finds no bank, while `mb-graph.sh` would walk up. Possible follow-up: put the walk-up in the shared `findBank`.
- The nudge runs after the tool (`tool_result` appends the hint), because a Pi `tool_call` handler can block or mutate but cannot add context.

## Risks / follow-ups

- Existing users whose model lives only in the OS temp dir keep reading it there. After macOS purges it, the next online build re-downloads into `~/.cache/fastembed`. Offline before that, search answers BM25 with the diagnosis.
- `.graph-catchup.log` is written by the Pi process when the background catch-up finishes. If Pi exits first, the detached catch-up still completes (its builder is bounded by `MB_GRAPH_CATCHUP_BUDGET`), but no log is written.
- Each structural bash/grep result spawns `_lib.sh` resolution plus the nudge script (bounded to 10 s, fail-open).
