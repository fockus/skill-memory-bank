# Сравнение: mattpocock/skills vs Memory Bank (/mb discuss → sdd → plan)

Дата: 2026-07-17. Источник: https://github.com/mattpocock/skills (клон, коммит HEAD на дату).
Цель: гэп-анализ против вижена «брифинг → качественная спека с эвалами → умная декомпозиция → ICE-роадмеп → детерминированный беклог → ADaPT adaptive replan».

## 1. Скилы Мэтта Покока — суть и оценка

### grill-me / grilling (7 строк)
Безжалостное интервью: одна ветка дерева решений за раз, рекомендация на каждый вопрос,
факты ищет сам, решения — только у пользователя, не действовать до shared understanding.
- **+** Минимализм; универсальность (любое решение, не только перед планом); model-invocable по триггер-фразам.
- **−** Нет артефакта на выходе (только разговор), нет валидации, нет traceability, нет resume.
- Наш `/mb discuss` уже впитал их идеи (grilling rules 1–10 явно цитируют grill-me/grill-with-docs) и добавил Research digest, EARS, Decision ledger.

### batch-grill-me (in-progress, но важный)
Интервью **раундами по фронтиру**: все вопросы, чьи пререквизиты закрыты, задаются одним
пронумерованным раундом с рекомендациями; факты добывают **параллельные сабагенты, не блокируя фронтир**.
- **+** Кардинально быстрее для больших спек, чем строгий one-question-per-turn.
- **−** Раунды из 8+ вопросов могут перегружать пользователя.
- У нас такого режима нет — discuss жёстко «один вопрос за ход» (правило 6).

### grill-with-docs = grilling + domain-modeling
Артефакты рождаются **по ходу** интервью: глоссарий `CONTEXT.md` (ubiquitous language, обновляется
inline при каждом разрешённом термине), ADR с тройным гейтом (hard to reverse + surprising + real trade-off),
сверка терминов с кодом, стресс-тест конкретными сценариями.
- **+** Глоссарий как отдельный концерн («CONTEXT.md — только глоссарий, не спека и не скретчпад»); ADR-гейт из 3 критериев; multi-context через CONTEXT-MAP.md.
- **−** Всё прозой, ноль автоматики.
- У нас: ADR в backlog.md + AGR-реестр есть; **глоссария/ubiquitous language нет вообще**; артефакт пишем в конце, а не inline.

### diagnosing-bugs
Дисциплина «feedback loop first»: Фаза 1 закрыта только когда есть **одна именованная команда,
уже запущенная хоть раз**, которая red-capable (ловит именно этот симптом) + детерминированная +
быстрая + agent-runnable. «Нет red-команды — нет Фазы 2». Дальше: минимизация репро → 3–5
фальсифицируемых гипотез (показать пользователю) → инструментирование с тегами [DEBUG-xxx] →
regression test до фикса (или честное «нет правильного seam — это само по себе находка») →
post-mortem с хендофом в архитектурный скил.
- **+++** Главная кража для нас: **паттерн «эвал раньше работы» с проверяемым критерием готовности гейта**. Это ровно то, что вижен требует от спек: детерминированная команда-проверка, определённая до реализации.
- **+** Честная эскалация («не могу построить loop → стоп, список попыток, запрос артефактов»).
- **−** Как и всё у них — конвенция без тулинга.
- У нас в MB-скиле нет команды диагностики багов вовсе (есть только сабагент debugger).

### to-spec
Синтез спеки из текущего разговора **без интервью** → публикация в трекер с label `ready-for-agent`.
Ключевое: шаг 2 — **сначала набросать test seams** (предпочесть существующие, максимально высокий,
идеал — один) и подтвердить их с пользователем. Принцип долговечности: **никаких путей файлов и
сниппетов** — устаревают (исключение: сниппет из прототипа, кодирующий решение).
- **+** Seam-first testing decision — у нас этого шага нет ни в discuss, ни в sdd; durability-принцип; один шаг от разговора до опубликованного артефакта.
- **−** Нет EARS, нет REQ-ID, нет валидации, нет traceability, user stories «LONG list» без структуры приёмки.

### triage
Стейт-машина для issues/PR: категории bug/enhancement × статусы needs-triage / needs-info /
ready-for-agent / ready-for-human / wontfix. Перед грилом — **verify the claim** (воспроизвести баг,
прогнать diff PR). Redundancy-check (не реализовано ли уже) + KB отклонённых запросов `.out-of-scope/*.md`
(при новом похожем запросе — поднять прецедент). Outcome `ready-for-agent` = **agent brief** —
контракт для AFK-агента: behavioral-not-procedural, без путей/номеров строк, полные acceptance
criteria, явный out-of-scope.
- **+++** Референс для нашего беклога: статусная модель с петлёй needs-info, KB отказов, durable agent briefs.
- **−** Заточен под GitHub-трекер; лейблы требуют setup-скила.
- У нас: I-NNN c NEW/TRIAGED/DONE — плоско, нет needs-info-петли, нет wontfix-KB, нет иерархии подзадач, нет стандарта брифа для ready-элементов.

### to-tickets
План/спека/разговор → **tracer-bullet тикеты**: каждый — вертикальный срез через все слои
(schema+API+UI+tests), **демонстрируемый сам по себе**, размером в один свежий контекст.
Каждый тикет объявляет **blocking edges** (DAG); исполняется **фронтир** (все тикеты с закрытыми
блокерами — параллельно). Wide-рефакторы — исключение: **expand–contract** (добавить новое рядом →
мигрировать батчами по blast radius → удалить старое), каждый батч — тикет. Шаг 4 — quiz the user
о гранулярности и корректности рёбер.
- **+++** DAG на уровне задач + фронтир = готовая модель для параллельных агентов из вижена; вертикальные срезы против нашего риска горизонтальной нарезки; expand–contract кодифицирован.
- **−** Нет численных лимитов размера («fits a fresh context window» — на глаз); нет привязки к требованиям (никаких Covers/REQ).

### wayfinder (бонус, не в списке, но закрывает пункт вижена)
Работа «больше одной сессии, в тумане» → **карта decision-тикетов** на трекере: каждый тикет —
вопрос (research/prototype/grilling/task), размер — одна 100K-сессия, blocking edges, фронтир,
карта — индекс решений (одна строка на закрытый тикет), «Not yet specified» = туман войны.
Это их ответ на «большую задачу бить на несколько спек, каждую — через своё интервью».
- У нас аналог — конвенция umbrella-spec + JIT-слайсы (AGR-001), но это практика, не механизм.

## 2. Где мы уже сильнее (по нашим командам)

1. **Детерминированная валидация**: mb-ears-validate, mb-spec-validate (маркеры, Covers/DoD/Testing, orphaned REQ, GWT-скан), mb-req-next-id — у них ноль исполняемого тулинга вокруг спек, всё прозой.
2. **Traceability**: матрица REQ → Plan → Test (mb-traceability-gen) — аналога нет.
3. **Исполняемые задачи + governed execution**: `<!-- mb-task:N -->` как first-class артефакт, mb_work_items.py, /mb work с verify → review ensemble → judge, severity/judge-гейты, бюджеты, protected paths, pivot. Их `/implement` — 8 строк («use /tdd, run tests, /code-review, commit»).
4. **Research-grounded интервью**: Phase 0 digest с обязательными цитатами file:line/URL, «рекомендация без цитаты = guess»; у grilling только «look up facts».
5. **Decision ledger + AGR-реестр** (supersedes, kill-switch), append-only progress, монотонные ID.
6. **Численные лимиты декомпозиции**: Sprint ≤200k токенов, 3–7 stages, ≤15 файлов, ≤60 тестов, hard-check с критериями сплита — у них «на глаз».
7. **Инфраструктура**: roadmap-autosync из frontmatter (depends_on/parallel_safe), checklist-sync, COORDINATION.md для параллельных сессий, pipeline.yaml, кросс-платформенные адаптеры, session memory/recall/code graph, питающие Phase 0.

## 3. Гэпы против вижена (что забрать/построить)

| # | Гэп | Референс | Что сделать |
|---|-----|----------|-------------|
| G1 | `/mb sdd` — скаффолд, не пайплайн («does not auto-generate design/tasks content») | вижен | sdd = единый конвейер: (интервью если нет context) → requirements → design → **сгенерированный tasks.md с планом внутри**; /mb plan остаётся только для «спека не нужна», план хранится рядом со спекой |
| G2 | Нет eval-first гейта на уровне спеки/задачи | diagnosing-bugs Phase 1 | Каждой задаче — поле **Eval:** именованная команда + ожидаемый red/green-сигнал, определённая ДО реализации; «нет red-capable команды — задача не ready». GWT-гейт (require_scenarios) сделать исполняемым, не прозой |
| G3 | Нет seam-шага | to-spec §2 | В design.md-интервью: набросать test seams (существующие > новые, максимально высокий, идеал один) и подтвердить с пользователем |
| G4 | Нет механизма мульти-спековой декомпозиции (~1M токенов/спека) | wayfinder | Команда-«карта»: umbrella-спека → child-спеки как decision/spec-тикеты, каждая проходит своё мини-интервью; кодифицировать AGR-001 из практики в механизм |
| G5 | tasks.md — линейная нумерация, нет DAG | to-tickets | **Blocked-by рёбра на уровне задач** + исполнение фронтира → параллельные агенты; roadmap-уровень (depends_on) уже есть, нижний — нет |

| G9 | Беклог плоский | triage | Стейт-машина (needs-info-петля, ready-for-agent, wontfix + `.out-of-scope/` KB), parent/child иерархия I-NNN, agent-brief-формат (behavioral, без путей файлов) для ready-элементов |

## 4. Приоритет внедрения (черновой)

1. **G1+G2** — sdd как полный пайплайн с eval-first задачами (ядро вижена).
2. **G5+G6** — DAG задач + вертикальные срезы (разблокирует параллельных агентов).
3. **G7+G8+G9** — ICE-роадмеп с %, беклог-стейт-машина (детерминированный слой, чистые скрипты).
4. **G10** — ADaPT-эскалация в /mb work.
5. **G4** — мульти-спековая карта (wayfinder-механизм).
6. **G3, G11, G12, G13, G14** — усиления интервью и durability.
