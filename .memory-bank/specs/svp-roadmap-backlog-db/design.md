## Architecture

Чисто **скриптовый слайс** (LLM-слоя почти нет): расширение `mb-roadmap-sync.sh` (ICE/pin-порядок
Next/Parallel-safe, прогресс, `## Group:`-секции, read-only `--check`), расширение `mb-idea.sh`
(общий lock + глобальный аллокатор + similarity-хук + типизированный SPEC-writer) и
`mb-idea-promote.sh` (общий lock + приведение к машине C3, C7), новый `mb-backlog-state.sh`
(переходы, иерархия, out-of-scope), новый `mb-backlog-migrate.sh` (паттерн migrate-structure,
финальная таблица легаси-статусов), новый `mb-bank-lint.sh`, общие примитивы в `scripts/_lib.sh`
(lock-хелпер C6 + аллокатор `I-NNN` C6). Prompt-слой: `commands/mb.md` (idea/agree-блоки упоминают
статусы), `references/templates.md` (frontmatter-схема), `CLAUDE.md`-инварианты; `commands/discuss.md`
не трогается.

`mb-roadmap-sync.sh` расширяется как источник данных: сегодня он сканирует только `plans/*.md`;
для Group-секций (REQ-003) он ДОПОЛНИТЕЛЬНО сканирует `specs/*/requirements.md` frontmatter
(`group`, `ice`, `pin`, `blocked_by`). Это два независимых источника (планы и спеки), объединяемых
только внутри рендера — оба используют один и тот же C1-словарь полей и один и тот же
приоритет-алгоритм C2.

## Interfaces

### C1. Frontmatter-схема ICE (входной контракт, потребляемый, не изобретаемый)

Group frontmatter зафиксирован родителем (`sdd-vision-pipeline/design.md` Interfaces п.4, ревизия 3)
и физически присутствует во всех 8 child-спеках группы (`specs/svp-*/requirements.md`). Хранятся
**компоненты**, а не готовый балл (D-14: цифры ICE — предложение LLM, подтверждает пользователь):

```yaml
topic: <slug>
group: <slug>
ice: {impact: <1..10>, confidence: <1..10>, ease: <1..10>}  # flow-style mapping, РОВНО одна строка
ice_confirmed: <true|false>    # ОПЦИОНАЛЬНО, дефолт false — пользователь подтвердил цифры LLM
blocked_by: [<spec-slug>, ...] # CSV-список topic-слагов других спек группы, [] если нет
pin: <positive integer>        # ОПЦИОНАЛЬНО — ручной override порядка, отсутствует по умолчанию
covers_umbrella: [...]
status: draft | ready | done
```

**Score считает скрипт, не человек**: `score = impact × confidence × ease` (диапазон 1..1000),
вычисляется при КАЖДОМ рендере, никогда не хранится во frontmatter и никогда не парсится обратно из
`roadmap.md` (тот же анти-round-trip-инвариант, что у процентов, REQ-012).

**Грамматика разбора** (`ice`-значение): строка обязана быть flow-mapping `{k: v, k: v, k: v}` с
РОВНО тремя ключами `impact`, `confidence`, `ease` (порядок ключей произволен, дубли запрещены),
каждое значение — целое `1..10` включительно. Причина flow-style: сегодняшний `parse_frontmatter`
(`mb-roadmap-sync.sh:66-76`) — построчный `partition(":")`, для которого flow-mapping разбирается
как единое значение, а block-style рассыпается на псевдо-ключи верхнего уровня.

Тот же набор (`ice`, `ice_confirmed`, `pin`, `group`) распространяется этим слайсом и на **планы**
(`plans/*.md` frontmatter) — сегодня ни один план его не несёт, это новая, полностью опциональная
надстройка (сценарий 1 использует синтетические тестовые планы, не существующий roadmap).

**Деградация (всё graceful, ни один вход не роняет sync)**:

| Вход | Ordering | lint |
|---|---|---|
| `ice` отсутствует | «no-ice tail» — конец секции, не ломает сортировку остальных | warning `no_ice` |
| `ice` валиден, `ice_confirmed` отсутствует/`false` | участвует нормально (подтверждение НИКОГДА не влияет на порядок) | warning `ice_unconfirmed` |
| `ice` есть, но не flow-mapping / не 3 ключа / дубль ключа / не целое / вне `1..10` | как no-ice tail | **error** `invalid_ice` |
| `ice` block-style (`ice:\n  impact: 8`) | как no-ice tail + stderr `[warn] plan <path>: ice uses block-style mapping; use flow-style {impact: N, confidence: N, ease: N}` (грамматика существующего block-style warning) | **error** `invalid_ice` |
| легаси plain-int `ice: 432` (черновая форма ревизии 2) | как no-ice tail | **error** `invalid_ice` |
| `pin` без `ice` | разрешён, pin один участвует в приоритете | — |

Plain-int `ice: <N>` нигде не выпущен (существует только во frontmatter 8 спек ЭТОЙ группы), поэтому
скрипта-мигратора frontmatter не требуется: `invalid_ice` — это error, а разовая правка 8 файлов
выполняется централизованно оркестратором (см. § Cross-slice requests). Скрипт обязан лишь
деградировать без падения, а не «понимать» plain-int.

`created` (для tie-break C2) НЕ отдельное новое поле: для спек это `created:` из
`context/<topic>.md` frontmatter (уже существует, см. `context/svp-brief.md:3`); для планов — дата,
встроенная в имя файла `YYYY-MM-DD_<type>_<topic>.md` (уже парсится `_DATE_PREFIX_RE`).

### C2. `mb-roadmap-sync.sh` — ICE/pin-порядок, прогресс, Group-секции, `--check`

**Два режима, а не один алгоритм (F-003).** Выбор режима — независимо для КАЖДОЙ рендеримой секции
(`Next`, `Parallel-safe`), по её собственному набору элементов:

1. **Legacy mode** — НИ У ОДНОГО элемента секции нет валидного `ice` и нет `pin`. Скрипт вызывает
   существующую `dependency_order(items)` (`mb-roadmap-sync.sh:175-212`) **без единого изменения**
   и возвращает её порядок и её предупреждения. Это и есть byte-identical деградация — она
   достигается вызовом старого кода, а не воспроизведением его поведения новым алгоритмом.
   `invalid_ice` НЕ активирует priority mode (банк с одним лишь битым `ice` остаётся byte-identical).
2. **Priority mode** — хотя бы у одного элемента секции есть валидный `ice` ИЛИ `pin`. Тогда и
   только тогда включается раундовый Kahn с приоритетом (ниже).

Почему не один алгоритм: раундовый Kahn и DFS дают РАЗНЫЙ порядок на валидном легаси-графе.
Эмпирика (закрывает F-003): элементы A, B, C в файловом порядке A/B/C, `A.depends_on = [C]` →
сегодняшний DFS даёт `C, A, B`, раундовый Kahn — `B, C, A`. Обещание «byte-identical» из ревизии 2
было ложным; здесь оно исполняется буквально — старым кодом.

**Priority mode — раундовый Kahn с приоритетом**:

1. На каждом раунде вычисляется **frontier** — элементы, все `depends_on` которых уже эмитированы
   (зависимости вне набора игнорируются, как и сегодня).
2. Frontier делится на `prioritized` (есть валидный `ice` ИЛИ `pin`) и `legacy_tail` (ни того ни
   другого).
3. `prioritized` сортируется тотальным компаратором (ключи по порядку):
   `pin` ↑ (беспиновые = `+inf`, т.е. после всех пинов) → `score` ↓ (нет валидного `ice` = `-inf`,
   т.е. в хвост `prioritized`) → `created` ↑ (отсутствует = `9999-12-31`, т.е. последним) →
   `topic` ↑ лексикографически → `rel` ↑ (repo-relative путь — финальный tie-break, гарантирует
   тотальный порядок даже при совпадении `topic` у двух планов).
4. `legacy_tail` сохраняет **исходный относительный порядок** (порядок попадания в `items` —
   сегодняшний `sorted(plans_dir.glob("*.md"))`), НЕ лексикографию по `topic`.
5. Эмитируются сначала `prioritized`, затем `legacy_tail`; оба удаляются из remaining; переход к
   следующему раунду.
6. Frontier пуст, а remaining непусто → цикл: печатается предупреждение сегодняшней грамматики
   `[warn] dependency cycle while sorting roadmap near <name>; keeping stable order`, где `<name>` =
   `path.name` ПЕРВОГО оставшегося элемента в исходном порядке; остаток эмитируется в исходном
   порядке, исключения нет. **Честная оговорка**: `<name>` в priority mode может отличаться от
   выбранного DFS'ом (DFS называет узел, на котором нашёл обратное ребро) — это не нарушение
   byte-identical, потому что priority mode включается ТОЛЬКО при наличии новых полей; легаси-цикл
   идёт по ветке 1 и печатает ровно сегодняшний текст.
7. Дублирующийся `pin` (два элемента с одинаковым `pin: N`) → у обоих участвуют остальные ключи
   компаратора (score/created/topic/rel), lint warning `duplicate_pin`; `pin` никогда не
   «перепрыгивает» через незакрытую зависимость — приоритет применяется ТОЛЬКО внутри уже готового
   frontier.
8. Тот же компаратор, применённый к спекам группы через `blocked_by: [<topic>...]` вместо
   `depends_on`, — внутригрупповой порядок REQ-003 (одна общая функция, два источника данных).
   Group-секция — новый рендер без легаси-вывода, поэтому она ВСЕГДА идёт priority-веткой; при
   полном отсутствии `ice`/`pin` у всех членов все они попадают в `legacy_tail` и печатаются в
   исходном порядке скана (`sorted(specs/*/requirements.md)` = `topic` по возрастанию).

**Единственный авторитет порядка группы (R2-003 / R2-003-R3)**: компаратор п.3 + правило `legacy_tail`
п.4 — единственный источник межспекового порядка для ВСЕЙ группы. `mb-work-resolve.sh --group` (S3-C5)
обязан потреблять его, а не собственный `ICE↓/topic↑` (запрос — § Cross-slice requests). Чтобы порядок
был исполним и воспроизводим у обоих потребителей, владелец фиксирует **исполнимый контракт источников
и ошибок** (S3 выравнивается под него, cross-package request):

- **Источники member-полей**: `created` спеки читается из `context/<topic>.md` frontmatter (уже
  существует); `group`/`ice`/`pin`/`blocked_by` — из `specs/<topic>/requirements.md`. Двух источников
  `created` быть не должно (S3 сегодня читает его из requirements.md — расхождение).
- **Отсутствующий или невалидный `ice` — НЕ ошибка исполнения** (не exit 2/3): член получает
  `ice=null`, классифицируется как `legacy_tail` и участвует в ТОМ ЖЕ порядке, что S4-C2; невалидный
  `ice` дополнительно даёт stderr-warning. `exit 3` остаётся только для malformed `pin`/`created`/
  `blocked_by`. Member-JSON схема — `"ice": <int|null>` (вычисленный score или `null`).
- **Общий физический файл фикстур — `tests/fixtures/svp_group_ordering.json`** (именуется дословно и в
  S4-C2/Task 6, и в S3-C5/Task 5). Он несёт четыре канонических кейса — **duplicate pin, missing ice,
  равный ICE, invalid ICE** — и обязывает **byte-identical порядок topic'ов** у обоих потребителей:
  roadmap-рендер (S4) и `mb-work-resolve.sh --group` (S3).

**Progress (REQ-002/REQ-012)** — источник истины: `python3 scripts/mb_work_items.py <path>` (уже
существует, не переизобретается). Для файла (план → `kind=stage`, спека `tasks.md` → `kind=task`):

- `total_dod = Σ len(item.dod_lines)` по всем items файла; `checked_dod` — количество строк вида
  `- [x]`/`- [X]` (обе нотации `mb_work_items.py` уже распознаёт).
- `progress_percent = floor(100 * checked_dod / total_dod)`; `total_dod == 0` → `0%` (легаси-файл
  без DoD-чекбоксов = отображается как `0%`, это существующая семантика `mb_work_items.py`, не
  новое поведение).
- Классификация каждого stage/task — `item.status` из `mb_work_items.py` напрямую:
  `done`→done, `in-progress`→in_progress, `pending`→planned (переименование только в отображении).
- Строка рендера: `progress=<N>% stages(done=<d>,in_progress=<i>,planned=<p>,total=<t>)` для планов
  или `tasks(...)` для спек — счётчики per-item (не per-checkbox).
- Пересчитывается заново при КАЖДОМ рендере из исходных файлов; никогда не парсится обратно из
  `roadmap.md` (устраняет round-trip-дрейф).
- Ручная правка числа внутри fences — не читается назад (per REQ-012); при следующем
  `mb-roadmap-sync.sh` она молча перезаписывается вычисленным значением; `mb-bank-lint.sh`
  (`--check`, ниже) отдельно детектирует расхождение ДО перезаписи (`progress_mismatch`).

**Group-секции (REQ-003)** — новый рендер-проход по `specs/*/requirements.md` frontmatter,
группировка по `group:`; для каждой группы `## Group: <name>` внутри fences, члены в порядке п.8.

**Позиция и порядок групп (R3-007, полная грамматика для byte-level регрессии)**: Group-блоки
эмитируются ПОСЛЕ секции `## Linked Specs (active)` и ПЕРЕД закрывающим fence `<!-- /mb-roadmap-auto -->`
(порядок секций autosync-блока: `## Now (in progress)` → `## Next (strict order — depends)` →
`## Parallel-safe (can run now)` → `## Linked Specs (active)` → Group-блоки). Несколько групп
сортируются по slug **bytewise C-locale по возрастанию**. Заголовок каждой — ровно `## Group: <slug>`;
группы разделяет ровно одна пустая строка. Порядок членов внутри группы — компаратор п.8. Контент вне
fence не трогается. Без этой фиксации два корректных реализатора дают разный byte-output, и
regression/Eval не может выбрать канонический (T6 несёт фикстуру с двумя группами и обратным порядком
скана файлов, assert точной позиции и порядка).

Строка члена:

```
<topic> — ice=<score|no-ice|invalid>[ (unconfirmed)] — <status draft|ready|done> — progress=<N>% — blocked_by=<csv|none>
```

Суффикс ` (unconfirmed)` печатается, когда `ice` валиден, а `ice_confirmed` не равен `true` (D-14:
цифры — предложение LLM, пока не подтверждённое пользователем). Агрегированный прогресс группы —
среднее арифметическое `progress_percent` членов, округление floor.

**Наблюдаемый сигнал эскалации неподтверждённого ICE (AGR-021, REQ-013)**: когда рендеримый порядок
(любой секции `Next`/`Parallel-safe` или Group-блока) использует **хотя бы один** валидный, но
неподтверждённый `ice` (`ice_confirmed ≠ true`), `mb-roadmap-sync.sh` печатает в **stderr** РОВНО одну
сводную строку `unconfirmed_ice=<csv topic-слагов, отсортированных bytewise C-locale по возрастанию>`.
Это наблюдаемый триггер: оркестратор по нему ЭСКАЛИРУЕТ пользователю «подтверди/поправь приоритеты».
Порядок **никогда** не меняется из-за неподтверждённости (score считается и сортирует как обычно) —
эскалация не блокирует ordering. Подтверждение = флип `ice_confirmed: false → true` во frontmatter
`requirements.md` соответствующей спеки; писать этот флип вправе ТОЛЬКО оркестратор (D-23 «банк пишет
только оркестратор»; скрипта-writer'а frontmatter спеки в этом слайсе нет — `mb-roadmap-sync.sh`
frontmatter не мутирует, лишь читает). После флипа `(unconfirmed)`, warning `ice_unconfirmed` и слаг в
`unconfirmed_ice=` для этой спеки исчезают на следующем рендере. Когда неподтверждённых ICE нет, строка
`unconfirmed_ice=` не печатается вовсе.

**Источник множества групп и `orphan_group` (R2-006)**: группы, подлежащие рендеру, обнаруживаются
ТОЛЬКО сканом `specs/*/requirements.md` (`group:`). Осиротевшая группа не может прийти из этого же
источника, поэтому её источник задан отдельно и явно: перед рендером читаются существующие
`## Group: <slug>` заголовки **исключительно внутри текущего autosync-fence**; slug, присутствующий
там, но отсутствующий среди обнаруженных в `specs/*/requirements.md` (переименование/удаление
спеки), — это warning `orphan_group`, и в новый блок он не попадает (stale-заголовок исчезает).
Ручные `## Group:`-заголовки ВНЕ fences никогда не интерпретируются как данные реестра (S4-A-02).

**Bootstrap**: существующий ручной блок `roadmap.md § Group: sdd-vision-pipeline` переносится под
fences и удаляется как ручной текст (Task 6) — единственный источник группы теперь автосинк.

**`--check` (read-only, F-008)**: `mb-roadmap-sync.sh --check [mb_path]` вычисляет ожидаемый
autosync-блок **в памяти**, НИКОГДА не пишет на диск, сравнивает с текущим содержимым fences;
exit 0 — идентично, exit 1 — устарело (используется `mb-bank-lint.sh` для `progress_mismatch`
без дублирования логики рендера).

### C3. `mb-backlog-state.sh` — стейт-машина, иерархия, брифы, out-of-scope

**CLI**:
```
mb-backlog-state.sh transition <I-NNN> <NEW_STATE> [--reason TEXT] [--mb PATH]
mb-backlog-state.sh annotate <I-NNN> --brief <TEXT> [--parent <I-NNN|none>] [--mb PATH]
mb-backlog-state.sh list [--tree] [--mb PATH]
```

**Машина**: `NEW → NEEDS-INFO ⇄ TRIAGED → READY → IN-PROGRESS → DONE | WONTFIX` (дословно D-15);
допустимые рёбра: `NEW→NEEDS-INFO`, `NEEDS-INFO→TRIAGED`, `TRIAGED→NEEDS-INFO|READY`,
`READY→IN-PROGRESS`, `IN-PROGRESS→DONE|WONTFIX`. `DONE`/`WONTFIX` терминальны — из них рёбер нет.
Любой иной переход — domain-отказ. Алфавит: `NEW`, `NEEDS-INFO`, `TRIAGED`, `READY`, `IN-PROGRESS`,
`DONE`, `WONTFIX` — и ничего кроме (`PLANNED` в алфавит НЕ входит; его судьба — C4-таблица и C7).

**Общий transition-примитив (R3-002, однозначная сигнатура)**: `scripts/_lib.sh` экспортирует
`mb_backlog_transition_locked <backlog_path> <I-NNN> <NEW_STATE> [--reason TEXT] [--plan REL]`.
**Precondition**: вызывающий УЖЕ владеет `<bank>/.locks/backlog.lock`; функция сама лок **никогда не
берёт и не отпускает** (иначе она либо дедлочит promote, который уже держит лок, либо ломает его
atomic-write). Функция валидирует ребро C3 и гейты READY/WONTFIX, рендерит новый токен `<STATE>` плюс
опциональные изменения `**Reason:**`/`**Plan:**` в ОДИН temp-файл, затем делает ОДИН `mv`. stdout —
пуст; exit `0` успех, `1` domain-отказ (недопустимый переход / провал гейта), `2` malformed/not-found.
Публичную success-строку печатает вызывающий скрипт после `return 0`, не сама функция:
`mb-backlog-state.sh` владеет захватом лока и печатает `item=… old_state=… new_state=…`;
`mb-idea-promote.sh` (C7) зовёт ту же функцию с `--plan <rel>`, удерживая уже взятый лок, единой
записью статуса и `**Plan:**`-ссылки. Второй реализации машины в репо не существует. Имя и precondition
дословно отражены в Task 2 и Task 9.

**Заголовок записи** остаётся тем же regex-контрактом, который `mb-idea-promote.sh` использует уже
сегодня: `^### I-NNN — <title> \[<PRIO>, <STATE>[ <доп.детали>], <created-date>\]$` — `transition`
переписывает ТОЛЬКО токен `<STATE>` (первое слово второго поля), сохраняя любые доп.-детали после
него (например, дату завершения) байт-в-байт, если они уже были.

**Успех**: stdout `item=<id> old_state=<old> new_state=<new>`; **domain-отказ** (недопустимый
переход) → exit 1, stderr со списком допустимых переходов из текущего состояния; **usage/not-found**
(нет такого I-NNN, кривые аргументы) → exit 2. Диагностика — всегда в stderr, stdout — только
success-строка. Мутация — под lock C6, atomic-записью (temp + `mv`).

**READY-гейт (REQ-007, блокирующий, не warning)**: переход в `READY` требует блок `**Brief:**`
непосредственно в теле записи; brief обязан быть behavioral (описывать наблюдаемое поведение —
эвристика: содержит хотя бы один глагол-паттерн `should|shall|must|когда|если`) и НЕ содержать
путей файлов (`\S+/\S+\.\w+` или `:\d+`-паттернов номеров строк). Нарушение любого условия → exit 1
с точной причиной (`missing brief` | `contains file path` | `contains line number`), переход НЕ
применяется (никаких частичных мутаций).

**`annotate` — единственный writer блоков `**Brief:**`/`**Parent:**` (X5-01, потребители: ремедиация
C7 и эскалация S5)**: атомарно добавляет или заменяет РОВНО блоки `**Brief:**` (обязательный аргумент)
и `**Parent:**` (опциональный `--parent <I-NNN|none>`; `none` удаляет блок) в теле записи, ничего
больше не трогая; brief валидируется ТОЙ ЖЕ функцией, что READY-гейт (behavioral-эвристика + запрет
путей/номеров строк) — невалидный brief не пишется вовсе. Мутация — под lock C6, atomic-записью.
**Успех**: stdout `item=<id> annotated`; domain-отказ (невалидный brief, `--parent` на несуществующий
I-NNN или цикл) → exit 1; usage/not-found → exit 2. Без `annotate` состояние `READY` инструментально
недостижимо (гейт требует `**Brief:**`, а писателя тела записи в машине нет) — это закрывало бы
ремедиацию C7 и Task 4 слайса S5.

**`list` / `list --tree` — машинно-парсируемая грамматика (F-005)**. Ровно одна строка на элемент:

```
item=<I-NNN> state=<STATE> parent=<I-NNN|none> depth=<int≥0> title=<JSON-string>
```

- `list` — плоский, `depth=0` у всех, порядок по числовому `I-NNN` по возрастанию.
- `list --tree` — та же грамматика в pre-order: родитель печатается раньше всех своих потомков,
  siblings — по числовому `I-NNN` по возрастанию, `depth` = глубина в дереве (корни = 0).
  Вложенность выражается полем `depth=`, а не отступами (стабильный парс + стабильные тесты).
- `title` — компактный JSON-строковый литерал (`json.dumps(t, ensure_ascii=False,
  separators=(',',':'))`), что снимает вопрос экранирования кавычек/пробелов/юникода в заголовке.
- Ошибки — stdout ПУСТ, диагностика в stderr, exit 1, без частичного дерева:
  `code=missing_parent item=<I-NNN> parent=<I-NNN>` | `code=parent_cycle path=<I-a>-><I-b>-><I-a>`.
- Записи `## Out of scope` в `list` не печатаются (они вне рабочего реестра); их читает только
  similarity-хук.

**Иерархия (REQ-006)** — опциональная строка `**Parent:** <I-NNN|none>` в теле записи (по
умолчанию `none`, поле может отсутствовать целиком = `none`).

**WONTFIX + Out-of-scope (REQ-008)**: переход в `WONTFIX` требует непустой `--reason TEXT`; при
успехе весь блок записи (заголовок + тело) **физически переносится** из `## Ideas` в `## Out of
scope` (перемещение, не дублирование — единственный источник для similarity-поиска, никакого
второго индекса), с добавленной строкой `**Reason:** <TEXT>` в конце тела. ID/title/created-date —
байт-в-байт.

**Похожесть при создании (REQ-008, F-010)** — вызывается из `mb-idea.sh` ПЕРЕД записью нового
I-NNN (surfacing hook, T8): similarity считается ТОЛЬКО против заголовков записей секции
`## Out of scope`. Normalize: Unicode casefold, все не-alphanumeric → пробел, оставить уникальные
токены длиной ≥ 4 символов. `score = |candidate ∩ existing| / min(|candidate|, |existing|)`; пустые
множества → `score=0`. `score ≥ 0.5` — совпадение. При совпадении: печать
`similar_out_of_scope=<I-NNN> score=<0..1>` на stderr, создание отклоняется (exit 1), если не
передан явный `--force`; при нескольких совпадениях побеждает наименьший числовой I-NNN (для
детерминизма вывода). Никакого LLM/сетевого вызова — чистая локальная токенизация.
**Область действия гейта**: только записи типа IDEA. Регистрация спеки (заголовок с точным
префиксом `[SPEC:<group>] `, C4) similarity НЕ проходит — это механическая запись реестра, а не
идея; иначе S2-оркестратор (`svp-sdd-core/design.md:64-66`) мог бы быть заблокирован похожестью и
вынужден передавать `--force`, что сломало бы его call-site.

**CLI `mb-idea.sh` после S4 (F-010)** — расширение существующего позиционного контракта
(`mb-idea.sh:4-11`), а не замена:

```
mb-idea.sh [--force] [--] <title> [priority] [mb_path]
```

- `--force` принимается ТОЛЬКО первым аргументом и обходит ТОЛЬКО similarity-отказ; идемпотентность
  по title (`mb-idea.sh:40-62`) и валидацию priority он НЕ обходит.
- `--` завершает разбор опций (escape-hatch для заголовка, начинающегося с дефисов).
- Любой ДРУГОЙ первый аргумент, начинающийся с `--`, → exit 2 (usage) ДО любой мутации.
- **Честная оговорка о совместимости**: вызовы, чей первый аргумент не начинается с `--`, остаются
  byte-identical (поведение, stdout `I-NNN`, exit-коды). Единственная теряемая возможность —
  заголовок, начинающийся с `--`, без `--`-разделителя (сегодня создался бы как есть); ради
  честности это фиксируется здесь, а не умалчивается. Экзотика покрыта escape-hatch'ем `--`.
- stdout остаётся ровно `I-NNN` (контракт потребителей, включая S2).

### C4. `mb-backlog-migrate.sh [--dry-run|--apply] [mb_path]`

Паттерн `mb-migrate-structure.sh`: `--dry-run` — дефолт, вывод инвентаря без записи;
`--apply` — backup в `.pre-migrate/<ts>/` (тот же helper), затем мутация; второй `--apply` —
`actions_pending=0`, файл байт-в-байт не меняется, новый backup не создаётся (идемпотентность).
Мутация — под lock C6 и atomic-записью (temp + `mv`), как у всех writer'ов (NFR-003).

**Финальная таблица легаси-статусов** (инвентарь взят из реального `backlog.md`: `DONE <date>`,
`OPEN`(×3), `PROPOSED`(×1), `RESOLVED <date>[ — <hash>]`(×5), `DEFERRED`(×2), `DECLINED`(×11),
`PLANNED`(×1), `NEW`(×70)):

| Legacy token (первое слово 2-го поля) | Новый токен | Доп. действие |
|---|---|---|
| `NEW` | `NEW` | нет |
| `TRIAGED` \| `OPEN` \| `PROPOSED` | `TRIAGED` | нет |
| `PLANNED` | `IN-PROGRESS` | нет (S4-A-03) |
| `DONE` (bare или с датой) | `DONE` | нет — остаётся под `## Ideas` |
| `RESOLVED` (bare, с датой, с `— <hash>`) | `DONE` | доп. текст после токена сохраняется байт-в-байт |
| `DECLINED` | `WONTFIX` | блок **переносится** в `## Out of scope` (см. C3); `**Reason:**` НЕ добавляется — легаси-запись без причины помечается grandfathered (см. ниже) |
| `DEFERRED` | `TRIAGED` | нет |

**Read-compatibility (без `--apply`)**: легаси-записи читаются/отображаются как есть, без мутации;
статусы вне таблицы И вне алфавита C3 (если появятся) дают warning `unknown_legacy_state=<token>`,
не падение.

**Grandfather-правило (устраняет конфликт REQ-008 «WONTFIX требует reason» ↔ REQ-011 «легаси без
новых полей не портится»)**: `ready_without_brief`/«WONTFIX требует Reason» в `mb-bank-lint.sh`
применяется ТОЛЬКО к записям, содержащим хотя бы одну v2-метастроку (`**Type:**`, `**Parent:**`,
`**Brief:**`, `**Reason:**`) — чисто легаси-запись (ни одной v2-строки) исключена из этой проверки
навсегда, даже после смены токена статуса миграцией. **Мигратор НЕ штампует `**Type:** IDEA` на
исторические записи** — иначе предикат «чисто легаси» испарился бы и правило grandfather стало бы
мёртвой буквой (мигрированные `DECLINED`→`WONTFIX` без Reason немедленно зафлаговались бы). Мигратор
добавляет метастроки ровно в одном случае: типизация `[SPEC:<group>]`-записи (ниже).

**`[SPEC:<group>]`-реестр (REQ-009)** — типизация записи, созданной переходным writer'ом
(`sdd-vision-pipeline/design.md` Interfaces п.4, `svp-sdd-core/design.md` C7):
заголовок `### I-NNN — [SPEC:<group>] <child-topic> [PRIO, STATE, DATE]` →

```
### I-NNN — <child-topic> [PRIO, STATE, DATE]
**Type:** SPEC
**Group:** <group>
**Parent:** none
**Spec:** <child-topic>
```

Мигратор убирает ТОЛЬКО префикс `[SPEC:<group>] ` из заголовка (остаток заголовка становится
title), добавляет четыре метастроки; ID/priority/state/date/порядок/остальное тело — байт-в-байт.

**Production writer, а не только мигратор (R2-004)**: `mb-idea.sh` после S4 распознаёт точный
префикс заголовка `[SPEC:<group>] <child-topic>` и пишет типизированную форму СРАЗУ.

**Грамматика и fail-before-allocation (R3-010, точно)**: типизированная регистрация — это title,
матчащийся РОВНО `^\[SPEC:([a-z0-9][a-z0-9-]*)\] ([a-z0-9][a-z0-9-]*)$` (group = группа 1, child-topic
= группа 2). Любой title, начинающийся с литерала `[SPEC:`, но НЕ матчащий эту грамматику (`[SPEC:]`,
`[SPEC:g]` без топика, `[SPEC:g] a b` с пробелом в топике, uppercase, незакрытая `]`), — usage-ошибка:
exit `2`, stdout пуст, backlog байт-в-байт, **без аллокации `I-NNN`** (fail до мутации). Title, НЕ
начинающийся с `[SPEC:`, остаётся обычным IDEA-title. Task 8 Testing несёт валидный слаг + по кейсу на
каждую malformed-форму (пустая группа, пустой топик, пробел в топике, uppercase, отсутствующая `]`),
каждый доказывает отсутствие мутации/аллокации.

Для валидного матча:

- префикс из хранимого title убирается; атомарно эмитируются `**Type:** SPEC`, `**Group:** <group>`,
  `**Parent:** none`, `**Spec:** <child-topic>`;
- заголовочная строка сохраняет сегодняшнюю грамматику байт-в-байт; stdout остаётся `I-NNN`;
- обычная (не-SPEC) запись получает `**Type:** IDEA` — тип реестра проставляется на всех НОВЫХ
  записях единообразно (исторические не трогаются, см. grandfather выше);
- similarity-гейт к SPEC-записи не применяется (C3).

Зачем: по порядку исполнения группы S4 (ICE 432) идёт РАНЬШЕ S2 (400), поэтому S2 создавал бы новые
префиксные записи уже ПОСЛЕ разовой миграции — «мигратор без writer'а» оставлял бы реестр вечно
догоняющим. Call-site S2 при этом не меняется: он по-прежнему зовёт
`mb-idea.sh "[SPEC:<group>] <child-topic>"`. Мигратор после этого нужен ровно для записей,
созданных ДО апгрейда writer'а.

### C5. `mb-bank-lint.sh <roadmap|backlog|all> [--mb PATH]`

Ровно одна строка на находку, все значения свободного текста — JSON-строки (F-008):

```
severity=<warning|error> code=<code> file=<JSON-string> line=<int≥0> detail=<JSON-string>
```

- JSON-строки строятся `json.dumps(value, ensure_ascii=False, separators=(',',':'))` — это
  однозначно кодирует пробелы, кавычки, юникод и переводы строк (NFR-004 требует путь банка с
  пробелами).
- `file` — repo-relative POSIX-путь; `line=0` означает «находка файлового уровня, конкретной строки
  нет».
- **Детерминированный порядок вывода**: `file` ↑, затем `line` ↑, затем `code` ↑ (иначе вывод не
  воспроизводим между запусками и не тестируем побайтово).

**Коды (15)** — каждый со своим тест-кейсом (T4). REQ-004 прямо требует валидировать confirmation
marker, `pin` и `group`, а C4 требует Reason у v2-WONTFIX — эти поля получают исполнимые коды
(R3-003):

| Severity | Code | Условие |
|---|---|---|
| warning | `no_ice` | элемент секции/группы без `ice` (C1) |
| warning | `ice_unconfirmed` | валидный `ice` без `ice_confirmed: true` (D-14) |
| warning | `orphan_group` | `## Group: <slug>` внутри fence, которого нет среди `specs/*/requirements.md` (C2) |
| warning | `duplicate_pin` | два элемента одной секции с одинаковым `pin: N` (C2) |
| warning | `legacy_state` | токен статуса ∈ таблице C4 (`OPEN`/`PROPOSED`/`PLANNED`/`RESOLVED`/`DECLINED`/`DEFERRED`), detail называет целевой токен и `mb-backlog-migrate.sh` |
| error | `invalid_ice` | `ice` присутствует, но нарушает грамматику C1 (не flow-mapping / не 3 ключа / дубль / не целое / вне 1..10 / plain-int) |
| error | `invalid_ice_confirmed` | `ice_confirmed` присутствует и не равен литералу `true`\|`false` |
| error | `invalid_pin` | `pin` присутствует и не является base-10 целым `> 0` |
| error | `invalid_group` | `group` присутствует и не соответствует `[a-z0-9][a-z0-9-]*` |
| error | `invalid_blocked_by` | `blocked_by` присутствует и не является flow-list уникальных слагов той же грамматики `[a-z0-9][a-z0-9-]*` |
| error | `progress_mismatch` | `mb-roadmap-sync.sh --check` вернул exit 1 (C2 — логика рендера не дублируется) |
| error | `invalid_state` | токен статуса не в алфавите C3 И не в таблице C4 |
| error | `ready_without_brief` | READY-запись без валидного `**Brief:**` — включая уже существующие READY-записи, не только новые переходы; grandfather-исключение C4 |
| error | `wontfix_without_reason` | v2-WONTFIX (есть хотя бы одна v2-метастрока) без непустого `**Reason:**`; чисто-легаси WONTFIX grandfathered (C4) |
| error | `parent_cycle` | parent-цепочка не разрешается в дерево (включая ссылку на несуществующий I-NNN) |

Разделение `legacy_state` (warning) и `invalid_state` (error) — обязательное следствие REQ-011:
не-мигрированный банк обязан оставаться зелёным по errors и лишь громко подсказывать миграцию, иначе
`mb-bank-lint.sh` красит любой существующий банк в день релиза.

Exit: `0` — нет errors; `1` — ≥1 error; `2` — неверный вызов (например, неизвестный аргумент
раздела). Никогда не мутирует файлы банка (read-only во всех трёх режимах). Область скана: `roadmap`
— `roadmap.md` + питающий его frontmatter (`plans/*.md`, `specs/*/requirements.md`: `ice`,
`ice_confirmed`, `pin`, `group`); `backlog` — `backlog.md`; `all` — оба.

### C6. Общие примитивы в `scripts/_lib.sh`: lock + аллокатор `I-NNN`

**Lock (owner-marker, следует родительскому Interface 2 ревизии 4).** В `scripts/_lib.sh` выносятся
`mb_lock_acquire <lock_dir> <timeout> <ttl>` / `mb_lock_release <lock_dir> <token>` с liveness-reclaim,
но с маркером владельца вместо `owner`-файла и bulk-move (закрывает critical R3-001: `mv`-reclaim
ревизии 3 всё ещё допускал двух писателей).

**Полный I/O-контракт (потребители зовут по нему; реализатор НЕ восстанавливает контракт по чужому
private-коду `mb-agree.sh`):**

- `mb_lock_acquire <lock_dir> <timeout> <ttl>`: при захвате печатает в stdout **РОВНО** `<PID>-<RANDOM>`
  плюс `\n` и возвращает `0`; при таймауте — stdout **пуст**, stderr `code=lock_timeout lock=<JSON-string>`,
  exit `1`; при кривых аргументах (нечисловой `timeout`/`ttl`, пустой `lock_dir`) — stdout пуст, stderr
  `code=lock_usage`, exit `2`.
- `mb_lock_release <lock_dir> <token>`: stdout всегда пуст; удаляет ТОЛЬКО `<lock_dir>/owner.<token>`,
  затем пустой `<lock_dir>` (`rmdir`); возвращает `0`, если снял свой owner ИЛИ лок уже отсутствует;
  возвращает `1` при чужом токене (owner другого) и при этом **не удаляет ничего**.

**Алгоритм:**

- Захват — атомарный `mkdir "<lock_dir>"` (единственный гейт). Победитель немедленно создаёт РОВНО один
  маркер владельца — подкаталог `<lock_dir>/owner.<token>`, `<token> = <PID>-<RANDOM>`. Инвариант: 0 или
  1 маркеров `owner.*` внутри корректного лока.
- **reclaim ключуется на liveness владельца (`kill -0` по PID из токена), а НЕ на mtime/TTL** и никогда
  не двигает/не сносит лок целиком (протокол ниже);
- PID-reuse → консервативный НЕ-reclaim (громкий timeout, ноль записей: потеря доступности, не
  корректности);
- перечитывание owner-маркера непосредственно перед reclaim;
- безусловный учёт timeout на каждой итерации (никакого `continue` в обход `sleep`/счётчика);
- **никакого вторичного `.reclaiming`-мьютекса** (он сам был гонкой, D-23).

**Ровно одно расхождение с оригиналом — механизм критической секции** (родительский Interface 2,
ревизия 4): `mb-agree.sh` держит `<lock>/owner`-файл и сносит лок неатомарным `rm -rf`
(`mb-agree.sh:138`); helper держит маркер `<lock>/owner.<token>` и реклеймит targeted-`rmdir` именно
мёртвого токена. Reclaim НЕ использует ни `mv`, ни `rm -rf`.

**Дефект оригинала реален** (`mb-agree.sh:132-139`): токен перечитывается ПЕРЕД `rm -rf`, но не
атомарно с ним. Интерливинг, проходящий сквозь эту защиту: X и Y видят мёртвого владельца D → Y
делает `rm -rf` → Z успевает `mkdir` и записать свой owner (живой лок) → X исполняет свой уже решённый
`rm -rf` и сносит ЖИВОЙ лок Z → Z и W оба в критической секции. Тот же класс дефекта имел и
`mv`-вариант ревизии 3 (закрывается сейчас, R3-001): «отставший сносит/двигает УЖЕ ДРУГОЙ, свежий
каталог».

**Протокол reclaim (задаётся точно, чтобы имплементер не гадал)** — при доказанно мёртвом владельце
`D` (маркер `<lock_dir>/owner.<D>`, `kill -0 <PID_of_D>` провален):

1. `rmdir "<lock_dir>/owner.<D>"` — удаляет ТОЛЬКО маркер именно мёртвого токена. `ENOENT` (маркер уже
   убран другим reclaim'ером или заменён) → **отступить к общему `sleep`/timeout и owner-less-TTL
   пути, НЕ переходя к п.2**: право на `rmdir "<lock_dir>"` имеет только процесс, чей
   `rmdir owner.<D>` прошёл успешно — иначе отставший reclaimer сносит свежий лок в пустом окне
   между `mkdir` нового владельца и записью его маркера (уточнено 2026-07-19 по фиксу R3-001
   из ревью s4-t2).
2. `rmdir "<lock_dir>"` — проходит ТОЛЬКО если каталог пуст. `ENOTEMPTY` = внутри уже появился свежий
   `owner.<Z>` живого владельца → **отступить к общему `sleep`/timeout, ничего больше не трогая**.
   Успех → лок свободен.
3. Повторить `mkdir "<lock_dir>"` наравне с прочими контендерами; победитель атомарного `mkdir` один.

Почему гонка «отставший сносит свежий лок» закрыта целиком: reclaim целится в **именованный** мёртвый
токен `D` (`rmdir owner.<D>` не трогает `owner.<Z>`), а `rmdir "<lock_dir>"` доступен только
победителю п.1 — `ENOTEMPTY` дополнительно страхует, когда внутри уже есть живой `owner.<Z>`. Поздний
X после того, как Y уже реклеймил и Z захватил свежий лок, получает `ENOENT` на `rmdir owner.D` и
немедленно отступает, не трогая `rmdir lock` — свежий лок Z цел даже в пустом окне до записи
`owner.<Z>`. Симметрично на стороне захвата: acquire никогда не возвращает успех, если создание его
`owner.<token>`-маркера провалилось (иначе возможен фантомный держатель).

**Инвариант подтверждения поколения (ABA, R3-001, уточнено 2026-07-19 по ревью s4-zone-fix).** Победа
в `mkdir "<lock_dir>"` сама по себе НЕ даёт владения: owner-less-TTL reclaimer мог за окно между нашим
`mkdir lock` и `mkdir owner.<token>` снести наш каталог, создать НОВОЕ поколение и опубликовать в нём
свой `owner.<B>` — тогда наш маркер лёг уже в поколение B (классический ABA). Поэтому сразу после
успешного `mkdir "<lock_dir>/owner.<token>"` acquire подтверждает владение текущим поколением: успех
разрешён ТОЛЬКО когда наш `owner.<token>` — ЕДИНСТВЕННЫЙ `owner.*` в каталоге. При обнаружении
sibling-маркера acquire удаляет РОВНО свой `owner.<token>` (никогда чужой) и уходит на retry/timeout.
Двое одновременно увидеть «я единственный» не могут (у второго наш маркер уже присутствует и не
удалён), поэтому держатель всегда ≤ 1; наихудший случай — взаимный откат обоих контендеров с
последующей пере-сериализацией через `mkdir`-гейт и TTL (деградация в доступность, не в корректность).

**Owner-less окно и TTL**: лок существует, но `owner.*` внутри нет (окно между `mkdir` и записью
маркера, между `rmdir owner.<D>` и `rmdir <lock_dir>`, или crash в этом окне). Такой лок НЕ сносится
немедленно — только после `<ttl>` секунд устойчивого owner-less состояния (консервативно, чтобы не
гонять с почти-завершившимся reclaim'ером). Это единственная роль TTL — аналог «owner нечитаем» у
оригинала. Ни один шаг не сносит непустой лок и не удаляет чужой именованный owner — деградация всегда
в доступность (отступление/таймаут), не в тихую двойную запись.

**Важно для имплементера — почему это не повтор отвергнутого дизайна**: комментарий `mb-agree.sh`
(`:60-78`) фиксирует, что варианты со stale-break уже пробовались и были отвергнуты. Отвергнуты они
были за (а) ключевание решения на mtime/TTL, который не отличает «осиротел» от «владелец жив и просто
занят дольше TTL», и (б) вторичный `.reclaiming`-мьютекс с собственным blind-`rm -rf` уровнем ниже,
позволявший `continue` пропускать учёт timeout. Контракт выше сохраняет главное завоевание оригинала —
**reclaim ключуется на liveness** — и НЕ вводит вторичного мьютекса; при этом он не использует ни
`mv`, ни `rm -rf`, а реклеймит targeted-`rmdir` именованного мёртвого токена, чего отвергнутые
варианты не делали. Читать `mb-agree.sh:56-116` перед реализацией обязательно (D-29): там четыре
disproved-итерации со стресс-тестами `tests/bats/test_mb_agree.bats`.

Отсюда — устранение внутреннего противоречия ревизии 2 (R2-001): helper **НЕ** «byte-identical
копия». Формулировка контракта: *то же liveness-решение, другой механизм критической секции
(owner-marker + targeted `rmdir` вместо `owner`-файла + bulk-`rm -rf`)*. Что это значит для
контрактного теста (T2):

- **Parity-часть**: общие фикстуры прогоняются против приватных функций `mb-agree.sh` и против
  нового helper'а — вердикты обязаны совпадать по ОБЩИМ **поведениям** (захват через атомарный
  `mkdir`; отказ при живом владельце; reclaim мёртвого владельца; TTL только в owner-less/нечитаемом
  окне; release только своим токеном; соблюдение timeout). Тест проверяет поведение, а не внутреннюю
  раскладку файлов, поэтому разная критическая секция (owner-файл vs owner-marker) паритет не ломает.
- **Divergence-часть**: кейс отставшего reclaim'ера + вклинившегося нового владельца (X/Y видят
  мёртвого D; Y реклеймит; Z захватывает свежий лок; поздний X исполняет решение) — helper обязан
  гарантировать одного держателя (`owner.<Z>` цел, X получает `ENOENT`+`ENOTEMPTY`); `mb-agree.sh`
  этот кейс НЕ обязан проходить, его ожидаемый результат зафиксирован в тесте как известный дефект.
- `mb-agree.sh` НЕ рефакторится этим слайсом (вне scope, риск регресса стабильного скрипта, 4
  итерации + стресс-тесты `tests/bats/test_mb_agree.bats`); новый helper используется ТОЛЬКО
  новым/расширяемым backlog-кодом. S3 (`svp-parallel-engine`) обязан потребить готовый helper, а не
  копировать пятую реализацию лока (родительский Interface 2, мягкая зависимость).

**Аллокатор `I-NNN` — глобальный по банку (F-012, критично).** Сегодня `mb-idea.sh:65` берёт максимум
ТОЛЬКО из `backlog.md`. Это не гипотеза, а зафиксированный дефект этого репо: запись
`backlog.md` I-079 документирует реальную коллизию — «на Task 11 скрипт выдал `I-075` (максимум
backlog был `I-074`), столкнувшись с существующей записью `I-075` в `progress.md`; пришлось руками
исправлять на I-078», что нарушает инвариант «I-NNN никогда не переиспользуются» (`CLAUDE.md`).

`mb_next_backlog_id <bank>` в `scripts/_lib.sh` — **единственный** аллокатор; ни один writer не
реализует свой:

- вызывается ТОЛЬКО при удерживаемом `<bank>/.locks/backlog.lock` (под lock'ом гонка невозможна);
- **stdout-контракт**: при успехе печатает **РОВНО** `I-NNN` (префикс `I-` + `%03d`) плюс `\n` и
  возвращает `0`; любой фатальный сбой скана/переполнения оставляет stdout **пустым** и возвращает `1`
  (потребитель отличает выданный ID от отказа по коду, не по парсингу stdout);
- `next_id = max(все найденные I-[0-9]{3} по источникам ниже) + 1`, формат `%03d`;
- **источники (исчерпывающе, по фактам репо)**:

| Источник | Обязателен | Почему |
|---|---|---|
| `backlog.md` | да | записи-идеи `### I-NNN — ` |
| `progress.md` | да, если существует | несёт implementation-записи `I-NNN` — ровно источник коллизии I-079 |
| `progress-archive.md` | если существует | `/mb consolidate` физически ПЕРЕНОСИТ progress-записи сюда (`scripts/mb-consolidate.sh:24`) → после консолидации ID покидают `progress.md` |
| `index.json` | если существует | производный, но дешёвый и просимый самой записью I-079 («and ideally index.json») — защищает от ID, удалённого из живых источников |

- **НЕ источники** (и это осознанно): `status.md`, `roadmap.md`, `checklist.md`, `notes/`,
  `session/` — только ЦИТИРУЮТ ID, выданные источниками выше (эмпирика: их максимум ≤ максимума
  `backlog.md`); `.index/`, `.pre-migrate*/`, `.migration-backup-*/`, `session/archive/` —
  производные/бэкап-деревья (скан бэкапа воскрешал бы намеренно удалённые записи).
- нечитаемый/битый ОПЦИОНАЛЬНЫЙ источник → `[warn] backlog id scan: unreadable source <path>;
  ignored` и продолжение; нечитаемый ОБЯЗАТЕЛЬНЫЙ источник → exit 1 без аллокации (fail fast:
  выдать ID, не увидев `backlog.md`, хуже, чем не выдать).
- переполнение (`max ≥ 999`) → exit 1 с громким сообщением; расширение формата ID вне scope.

`mb-idea.sh`, `mb-idea-promote.sh`, `mb-backlog-state.sh`, `mb-backlog-migrate.sh` берут
`mb_lock_acquire "<bank>/.locks/backlog.lock" "${MB_BACKLOG_LOCK_TIMEOUT:-10}"
"${MB_BACKLOG_LOCK_TTL:-120}"` ДО аллокации/мутации и освобождают его сразу после atomic-записи
(temp-file в директории банка + `mv`/`os.replace`, fsync где доступен).

**Весь путь read → decide → write держится под одним локом (R3-001, устранение TOCTOU)**: writer не
имеет права читать состояние, отпустить лок и потом писать — иначе два одинаковых title дают два блока
и два ID. Конкретно:

- `mb-idea.sh` берёт `backlog.lock` **ДО** title-idempotency-проверки (`mb-idea.sh:40-62`) и
  similarity-lookup (C3), перепроверяет обе под локом, зовёт аллокатор и держит лок сквозь `rename`;
- `mb-backlog-migrate.sh --apply` берёт лок **ДО** чтения источника и создания backup и держит его
  сквозь backup + `rename`;
- `mb-backlog-state.sh`/`mb-idea-promote.sh` держат лок сквозь `read state → validate edge → atomic
  write` (общий transition-примитив C3 не берёт лок сам — precondition «caller уже владеет локом»).

Контрактный тест T9: два одинаковых title под конкурентными процессами дают ОДИН блок и ОДИН общий ID.

**Ограничение для не-shell потребителей (X6-01)**: владелец лока — PID вызывающей оболочки, а
reclaim ключуется на его liveness (`kill -0`). Python/Node-потребитель, зовущий хелпер через
одноразовый `bash -c`, делает владельцем эфемерный процесс, умирающий сразу после захвата — любой
контендер увидит мёртвого владельца и мгновенно реклеймит ЖИВОЙ лок. Правильный паттерн: держателем
лока выступает bash-обёртка, живущая всю критическую секцию, а не-shell писатель — её дочерний
процесс (так делают `mb-docs-apply.sh` в S6 и `mb-work-claims.sh` в S3).

### C7. `mb-idea-promote.sh` — приведение к машине C3 (R2-002)

Сегодня скрипт принимает `NEW|TRIAGED` и пишет токен `PLANNED` (`mb-idea-promote.sh:69-75` и
`:102-107`), которого в алфавите C3 НЕТ. Без явной миграции скрипта каждый его вызов после S4 сажал
бы в беклог состояние вне алфавита (`invalid_state`) — тихая поломка. Контракт после S4:

- **`PLANNED` не пишется никогда.** Единственный записываемый переход — `READY → IN-PROGRESS`,
  выполняемый ОБЩИМ transition-примитивом C3 (той же валидацией машины), под lock'ом C6.
- Порядок операций: (1) lock; (2) прочитать состояние; (3) валидировать `READY`; (4) создать план
  (`mb-plan.sh`); (5) применить `READY→IN-PROGRESS` + `**Plan:**`-ссылку ОДНОЙ atomic-записью;
  (6) unlock. Отказ на шаге 3 → ни плана, ни мутации (никаких частичных эффектов).
- **Partial-failure после создания плана (R3-008, громкий идемпотентный исход)**: если шаг 4 успел
  (план создан), а шаг 5 (atomic backlog-write) или последующий sync упал — exit `1` и stderr
  `code=promote_partial plan=<repo-relative-path> backlog_updated=<true|false>`. **Повторный** promote
  того же `I-NNN` ОБЯЗАН обнаружить ровно этот существующий план, НЕ создавать второй план и
  идемпотентно дозакрыть недостающий шаг (backlog-ссылку/состояние либо sync). Ни один сбой не
  репортится как успех. Task 9 Testing несёт fault-injection после создания плана и после backlog-
  `rename`: в обоих случаях повторный вызов оставляет ровно один план и ровно одну `**Plan:**`-ссылку.
- Матрица входных состояний:

| Состояние записи | Поведение | Exit |
|---|---|---|
| `READY` | план + `READY→IN-PROGRESS` | 0 |
| `NEW` \| `NEEDS-INFO` \| `TRIAGED` | отказ + ремедиация (цепочка до READY) | 2 |
| `IN-PROGRESS` | «уже в работе» | 2 |
| `DONE` \| `WONTFIX` | «уже закрыта» (сохраняет сегодняшнюю семантику DONE/DECLINED) | 2 |
| легаси-токен таблицы C4 (`PLANNED`/`DEFERRED`/`OPEN`/`PROPOSED`/`RESOLVED`) | отказ + «run `mb-backlog-migrate.sh`» | 2 |
| иное | unknown status | 1 |

Сегодняшние exit-коды сохраняются (0 OK; 1 missing/not-found/unknown; 2 domain-отказ; 3 invalid
type) — меняется набор состояний, дающих exit 2, а не грамматика кодов.

**Осознанная, документируемая смена поведения (не тихая)**: сегодня `NEW → promote` создаёт план;
после S4 это отказ с точной ремедиацией (`mb-backlog-state.sh transition <I-NNN> NEEDS-INFO` →
`TRIAGED` → `READY` (требует `**Brief:**`) → `mb-idea-promote.sh`). Это прямое следствие решений
пользователя: D-15 делает `READY` единственным предсостоянием `IN-PROGRESS`, D-20 требует бриф на
`READY`. Альтернатива «легаси-путь продолжает писать `PLANNED`» **отклонена**: она (а) возвращает
токен вне алфавита, который сама же C4-миграция только что убрала, и (б) делает READY-дисциплину
мёртвой буквой — обычные записи никогда не получают v2-метастрок, поэтому «чисто легаси»-ветка
осталась бы вечной веткой по умолчанию. Документируется T5 (`commands/mb.md` + `CLAUDE.md`),
тестируется T9.

## Decisions

S4-A-01…05 + D-14/15/20/31 — в context; ключевое: только скрипты пишут вычисляемые числа (REQ-012).
Ревизия 3 (2026-07-17):

- `ice` — **компоненты** `{impact, confidence, ease}` (1..10), score = I×C×E считает скрипт; plain-int
  ревизии 2 отменён как ошибка (эмпирика 8 frontmatter описывала черновик, а не контракт родителя);
  `ice_confirmed` — место для подтверждения пользователем (D-14).
- Byte-identical легаси-порядок достигается ВЫЗОВОМ старого `dependency_order()`, а не его
  воспроизведением: priority mode — отдельная ветка, включаемая только новыми полями (F-003).
- Аллокатор `I-NNN` — глобальный (backlog + progress + progress-archive + index.json), один helper;
  доказательство необходимости — запись I-079 в этом же беклоге (F-012).
